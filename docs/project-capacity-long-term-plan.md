# 正常开发期间保持项目小于 1 GB：长期减负分析

日期：2026-10-13（Australia/Sydney）。**仅分析，没有转码、删除、替换或迁移正式资源；没有修改构建配置。**

本文容量数值基于 2026-10-13 的审计快照，不代表当前工作目录的实时容量。文中的体积估算是待验证方案，不表示容量清理或正式资源优化已经完成。

## 资源构成

src 共 733,211,251 字节：src/music 665,315,229；src/hand 33,989,235；src/assets 29,391,727；其余约 4.52 MB。按扩展名统计，WAV 656,969,382、PNG 63,601,952、MP3 7,682,296 字节，其余为代码、配置、文档等。这两种统计口径相互交叉，不能相加。

音乐体积的主因是 22 首 BGM WAV，合计 **654,663,442 字节**，约占 src 的 89.3%。全部为 48 kHz、双声道、16 位 PCM，总时长 **3408.213 秒（56.80 分钟）**。其他 13 个 WAV 仅 2,305,940 字节。应优先分析 BGM，而不是删除语音、音效、牌面或3D手部图片。

## 优先方案：区分母带和播放资源

未来经用户单独批准，可将 22 首 BGM 的无损母带完整归档、校验后，用压缩格式作为仓库内唯一的正式播放版本。游戏运行所需的每首曲目仍须位于项目中，正常游戏不依赖外部母带，也不依赖联网下载。此步骤会改变正式资源，必须另行授权，不能在本次清理中实施。

可先比较 MP3 128/160/192 kbps 的候选样本；当前 musicRegistry 已支持 mp3/wav，并根据去掉扩展名的 basename 生成 builtinTrackId，因此保留目录与文件 basename 有利于保持 ID 稳定。正式实施仍需检查设置/播放列表/随机选择/旧存档，不能仅凭此推断完全兼容。Opus/AAC 等方案需要额外验证文件发现模式、注册表及目标浏览器解码，不在本轮默认引入。

按总时长×目标码率计算的理论播放资源大小如下，尚未实际编码，不含容器及元数据开销：

| 目标码率 | BGM 估算 | 相对 WAV 减少 | src 估算 | 单份 dist 估算 |
|---|---:|---:|---:|---:|
| 128 kbps | 54.53 MB | 600.13 MB | 133.08 MB | 129.12 MB |
| 160 kbps | 68.16 MB | 586.50 MB | 146.71 MB | 142.75 MB |
| 192 kbps | 81.80 MB | 572.87 MB | 160.34 MB | 156.38 MB |

不能把码率估算当作音质批准。候选必须逐首解码并检查时长、响度、削波、开头/结尾、循环边界、浏览器 seek，以及主页/对局/立直切换、暂停恢复和同局播放行为；最后由真人试听批准。保留曲目数、名称、音量语义和既有音乐功能。

不要在 src 中同时保留 WAV 母带与 MP3 播放副本：当前 eager glob 会纳入两种文件，可能引入同 basename 的重复 Track ID，也会让源目录和构建继续包含母带。仅做 lazy loading 能减少初次下载，不保证本地源目录/构建输出变小。

FFmpeg 的官方编码文档提供 libmp3lame 及音频码率选项；这里只用其支持的码率作为容量试算，不执行编码：[FFmpeg 音频编码文档](https://ffmpeg.org/ffmpeg-codecs.html#libmp3lame)。

## 构建、缓存与证据策略

当前 dist 729.25 MB，其主体是被构建复制的正式资源。构建压缩提示只涉及 JS，不会把 WAV 自动转成小型音频。应先减少正式播放音频体积，再限定项目内只保留一份构建输出。诊断/生产候选及验收快照不持续堆在 artifacts；按照候选身份归档到项目外并保留 manifest 与结果。

当前 node_modules（含 .vite）275.49 MB，npm cache 173.17 MB。保留依赖，不移动依赖目录，不随意删包内源文件、source map、许可证或传递依赖来勉强达标。可以定期清理可再生成缓存，但缓存清理只能短期腾出空间，不是长期容量保证。

Vite 官方说明 .vite 属于可再生成的依赖缓存；publicDir 的文件也会复制到 outDir。把 WAV 从 src 搬到 public 仍会占据项目容量和构建副本，不能解决主要问题：[Vite 缓存与静态目录说明](https://vite.dev/config/shared-options.html)。项目安装版本为 Vite 6，正式配置调整应以该版本本地类型/实现为准，不直接照搬当前网站的新版本选项。

按当前依赖、同规模 .vite、同规模 npm cache、一份 dist、所有正式曲目仍在项目中估算：128 kbps 方案约 **713.47 MB**；192 kbps 方案约 **768.00 MB**。均为场景估算，不是已测量结果；需要为依赖增长、截图、日志和新资源留余量。若持续保留多份构建或全部 WAV 母带，仍可能超标。

建议后续建立目录容量预算：正常开发目标 ≤800 MB，接近 900 MB 时提示，≥1,000,000,000 字节时容量验收失败。检测应包含实际 src、已安装依赖、缓存、dist 和测试输出，不通过把必要依赖移到项目外或只统计 Git 文件来达标。容量门禁只报告，不自动删除资源。

## 次要优化与实施顺序

图片约 63.60 MB，明显小于 BGM。可另行分析重复纹理、无损压缩和按实际像素需求生成运行纹理，但必须保护母图、透明边缘、牌面文字、色彩与冻结3D视觉。未确认无用的图片/手部包全部保留。GLTF/纹理优化须先确认实际加载文件，不因看似重复就删除正式资产。

建议顺序：完成本次归档清理并取得当前功能验收 → 独立制作少量BGM候选供试听 → 用户批准正式资源迁移方案 → 检查注册表和数据兼容 → 全量测试/构建/3D/音频网络验收 → 实测正常开发容量 → 设置预算监测。此文档没有授权后续资源变更。
