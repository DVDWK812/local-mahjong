# 开发者测试模式

测试模式是开发者专用的统一测试用例中心，可登记对局、回放、存档、导入版本、固定种子运行和界面交互用例。确定性对局仍加载到正式牌桌与正式规则引擎；测试中心不会自动写入普通继续游戏存档，生成的牌谱标记为 `source=test-mode`，需从工具栏显式导出。

## 启用方式

- Vite 开发环境（`import.meta.env.DEV`）自动显示首页“测试模式”入口。
- 非开发环境仅在构建时设置 `VITE_ENABLE_TEST_MODE=true` 时启用。
- 已启用时可用 `?testMode=1` 直接进入场景库；未启用的普通生产构建不会显示入口，也不会响应该参数。
- 测试场景库、牌桌工具栏和调试面板均显示“测试环境”标识。

## TestScenarioV1 格式

`version` 当前固定为 `1`。场景复用可序列化的 `FullRuleConfig` 和 `GameState`，并补充 `id`、名称、说明、关联审计编号、局序、全员手动列表、声明牌数、动态初始总点数、已使用岭上牌数、杠前活牌数、人工步骤和可选检查点。

`gameState` 保存四家完整手牌、牌河、副露、分数与临时状态，以及场风、局数、本场、供托、当前玩家、phase、当前摸牌、所有等待窗口、准确活牌顺序和固定 14 张王牌。内置场景的 `instanceId` 使用可读且稳定的 `<scenario-id>-<zone>-<index>` 形式，不依赖随机 UUID。

启动前会严格校验版本、字段路径、四名唯一玩家、实例 ID、每种牌/赤牌上限、声明牌数、手牌与 phase、牌墙和王牌、当前摸牌、共享宝牌槽、岭上记账、动态点数守恒及 pending 窗口。claimed 牌河历史继续沿用项目的受控历史别名语义；校验失败会列出路径和原因并阻止启动。

`TestScenarioV1` 的字段和 JSON 语义保持不变；旧文件继续由原 V1 校验器直接读取。测试用例中心只在外层包装该场景，没有为 V1 添加必填字段，也没有引入迁移要求。

## TestCaseDefinitionV1 用例类型

所有用例共享 `version`、`id`、`name`、`description`、可选 `relatedAuditId`、`category`、`expectedResults`、`manualSteps` 和 `tags`。`kind` 决定唯一执行器，`category` 只用于浏览和筛选，不参与执行分派。

- `PlayableTestCase`：包含原样的 `TestScenarioV1`，进入真实牌桌后只调用正式动作入口。
- `ReplayTestCase`：可附带测试牌谱、初始局和步骤；没有自动牌谱执行器时要求人工确认。
- `PersistenceTestCase`：声明往返或读/写/删失败模拟，只操作注入的测试 Storage 适配器。
- `ImportValidationTestCase`：保存输入 JSON、格式和预期是否有效，用于版本及导入边界。
- `SeededRunTestCase`：登记 seed、次数和运行器 ID；内置运行器使用确定性随机源和正式动作入口执行，并逐动作检查不变量。
- `UiInteractionTestCase`：登记路由和点击、按键、可见性、焦点或窗口尺寸步骤；没有 UI 执行器时要求人工确认。

内置或导入用例按八类展示：对局规则、计分与结算、牌谱与隐藏信息、存档与迁移、导入与版本、随机与压力、界面与键盘、STAB-001旧场景。六种 `kind` 均有内置登记样例；四个原 STAB-001 场景属于最后一类。

## 运行状态与失败报告

每个用例独立记录“未运行、运行中、通过、失败、需人工确认”。可操作对局点击后进入正式牌桌；其他类型调用与 `kind` 精确匹配的执行器。人工用例可在完成步骤后标记通过或失败。

统一失败结果包含用例 ID、关联审计编号、当前步骤、预期、实际、状态摘要及可选 JSON/文本产物。失败卡片提供“复制失败报告”和“导出相关JSON”；正式牌桌的不变量或动作异常也会转换为同一可序列化报告结构，同时保留当前场景。

## JSON 导入与导出

在用例中心粘贴 JSON 或选择 `.json` 文件：没有 `kind` 的旧 `TestScenarioV1` 继续校验后直接进入牌桌；带 `kind` 的 `TestCaseDefinitionV1` 校验后注册到对应分类。牌桌工具栏可导出当前状态为新的 `TestScenarioV1`、重置到最初状态、复制状态摘要，或导出本次正式事件记录器生成的测试牌谱。导出的场景再次导入应得到等价状态。

## 从牌谱创建场景

测试模式启用时，牌谱播放器显示“转为测试场景”。转换使用当前播放步骤的 `buildReplayState` 结果，并带入保存规则、四家状态、牌河、副露、牌墙、固定王牌、分数、供托、当前玩家和 phase。缺少完整活牌墙/14 张王牌的旧牌谱会禁用转换并显示原因；成功后场景脱离播放器，由正式引擎继续操作。

## 内置 STAB-001 场景

- `STAB-001-ANKAN`：当前玩家可立即暗杠。
- `STAB-001-MINKAN`：位于可直接选择大明杠的鸣牌窗口。
- `STAB-001-KAKAN`：已有碰副露且持有第四张牌，可立即加杠。
- `STAB-001-FOUR-KANS`：按说明连续执行四次暗杠，不依赖随机摸牌。

每个场景包含人工步骤和检查点，记录期望岭上牌 `instanceId`、新公开表宝原始槽位、活牌剩余变化及回放状态。

## STAB-002 存档回归用例

- `STAB-002-CHI-SAVE`：通过正式 `executeChi` 建立吃牌状态，再使用正式存档适配器保存和恢复；自动比较 claimed 牌河、`call.from`、副露实例和食替集合。
- `STAB-002-PON-SAVE`：通过正式 `executePon` 建立碰牌状态并完成保存/恢复差分。
- `STAB-002-MINKAN-SAVE`：通过正式 `executeKan(..., 'minkan')` 完成大明杠和岭上摸牌；从杠前状态启动正式事件记录器，恢复后比较岭上 `instanceId`、活牌墙、claimed 历史和副露来源。
- `STAB-002-INVALID-ALIASES`：自动篡改手牌与牌墙、手牌与副露、未 claimed 牌河与副露、一个 claimed 实例对应两个副露；每项必须被共享存档校验器拒绝并返回具体原因。

这些用例只向 `LocalStorageAdapter` 注入测试中心的内存 Storage，不接触普通继续游戏键。卡片展示自动检查的实际值和人工核对步骤，可复制或导出失败结果。

## STAB-003 牌谱可见性回归用例

- `STAB-003-HIDDEN-DRAW`：对手摸牌后弃牌前，已消费实例不进入公开权限且保持牌背。
- `STAB-003-PUBLIC-AFTER-DISCARD`：弃牌后只公开实际 `instanceId`，同牌型其他实例不继承权限。
- `STAB-003-CALL-PUBLIC`：在三局固定牌谱中分别验证吃、碰、大明杠的实际副露实例公开。
- `STAB-003-CAMERA-SWITCH`：四家视角依次计算自知集合，只有当前持牌玩家可见暗摸实例。
- `STAB-003-FULL-OPEN`：开启时暗摸牌与未来牌墙可见，关闭后权限集合与开启前完全一致。

五个用例均附带 `source=test-mode` 的确定性牌谱，可点击“运行用例”执行 instanceId 权限检查，也可点击“人工查看附带牌谱”进入正式牌谱播放器；退出测试牌谱后返回测试用例中心。没有修改 `ReplayRecord`、`RoundLog`、普通牌谱或普通存档的格式版本。

## STAB-005 供托结算回归用例

- `STAB-005-RON-1-STICK`：一根供托下荣和，检查结算快照与桌面清零。
- `STAB-005-TSUMO-4-STICKS`：四根供托下自摸，检查一次发放与点数守恒。
- `STAB-005-CHANKAN-STICKS`：抢杠和使用与普通和牌相同的共享结算语义。
- `STAB-005-MULTI-RON-STICKS`：多家荣和仍按既有顺序向首位赢家发放供托。
- `STAB-005-CUSTOM-STARTING-POINTS`：四家27000点，以108000而非100000作为动态守恒基线。

五个用例都是确定性的 `PlayableTestCase`，可直接进入正式牌桌查看结果弹窗并导出测试牌谱。调试面板同时显示结果中的结算前供托快照、权威桌面供托、玩家点数合计、场景声明的动态初始总点数和守恒结论。

### STAB-004 可见牌统计回归

- `STAB-004-CHI-VISIBLE-COUNT`：吃牌后保留 claimed 牌河历史，检查被鸣实例只计一次。
- `STAB-004-PON-VISIBLE-COUNT`：碰牌后检查三个不同物理实例计为三张。
- `STAB-004-MINKAN-VISIBLE-COUNT`：大明杠后检查四个实例计为四张，剩余数为零而非负数。
- `STAB-004-RED-FIVE-COUNT`：赤五与普通五按相同 `tile.id` 汇总，仍按 `instanceId` 去重。

四个用例均可进入正式牌桌人工查看。调试面板的“公开牌统计”按当前控制玩家视角显示 `tile.id`、唯一公开 `instanceId` 列表、`visibleCount`、`remainingCount` 和每个实例的来源区域；claimed 牌河与其唯一副露会显示为同一实例的两个来源，而不会重复计数。

### STAB-006 立直暗杠合法性回归

- `STAB-006-ANKAN-WAIT-UNCHANGED`：杠前后等待相同，真实 Board 显示暗杠按钮并可成功执行。
- `STAB-006-ANKAN-WAIT-CHANGED`：移除四张并固定杠面子后等待改变，UI 与底层同时禁止。
- `STAB-006-DRAWN-TILE-IN-QUAD`：摸入牌是四张同牌之一，杠前等待使用移除该摸入牌后的基准手牌。
- `STAB-006-NO-LEGAL-ANKAN`：没有四张同牌，UI、AI 与底层合法候选均为空。

调试面板的“立直暗杠共享判定”显示杠前等待、移除四张后的等待、共享判定结果、UI候选和底层 `canAnkan` 结果。场景只提供确定性初态；允许场景中的暗杠仍由正式 `executeKan` 执行，拒绝场景不会通过测试模式绕过规则。

### STAB-007 v1 存档兼容回归

- `STAB-007-MISSING-APPLIED-ROUND-IDS`：删除 `matchState.appliedRoundIds` 后加载，期望归一化为空数组并通过验证。
- `STAB-007-MISSING-SCORE-HISTORY`：删除 `matchState.scoreHistory` 后加载，期望归一化为空数组并通过验证。
- `STAB-007-MISSING-RULE-CONFIG`：删除完整顶层规则对象后加载，期望从 v1 可用数据安全推导并补齐完整规则。
- `STAB-007-MINIMAL-V1-SAVE`：同时删除全部可安全恢复的后增字段和规则对象，验证集中默认结构可恢复最小 v1 存档。

四个 `PersistenceTestCase` 都调用正式 `migrateSavedMatch` 与 `validateSavedMatch`，结果区显示迁移前字段、迁移后字段和验证结果；失败报告可复制并序列化。用例数据仅存在于测试中心执行上下文，不读取或写入普通继续游戏存档，SavedMatch 格式版本仍为 1。

### STAB-008 规则设置存储失败回归

- `STAB-008-GET-FAILURE`：模拟 `getItem` 抛出 `SecurityError`，确认返回默认配置和统一读取错误。
- `STAB-008-SET-SECURITY-ERROR`：模拟 `setItem` 因安全限制失败，确认内存设置立即生效、原持久化配置保留并显示非阻断提示。
- `STAB-008-SET-QUOTA-ERROR`：模拟 `QuotaExceededError`，检查配额错误分类及相同的非阻断语义。
- `STAB-008-REMOVE-FAILURE`：模拟 `removeItem` 失败，确认原配置没有被清空。

用例中心的“模拟存储失败”面板可为测试内存适配器选择读取、SecurityError 写入、QuotaExceededError 写入、普通写入错误或删除失败。该面板和四个自动用例均不读取或修改 `window.localStorage`；关闭测试模式后不会留下故障注入状态。

### STAB-009 牌谱版本策略回归

- `STAB-009-REPLAY-V0` / `V1` / `V2`：分别验证 ReplayRecord 旧版、当前版和未来版。
- `STAB-009-RAW-LOG-V0` / `V1` / `V2`：对裸 MatchLog 执行相同矩阵。

v1 输入显示“输入被接受”；v0 在没有明确迁移器时显示旧版本拒绝；v2 显示“不支持的未来版本”。拒绝结果统一包含格式类型、实际版本和支持版本。测试用例调用正式 `normalizeReplayRecord` 或 `deserializeMatchLog` 导入入口，不复制另一套版本判断，也不改变当前 v1 JSON 内容。

### STAB-010 确定性随机与压力测试

测试模式“随机与压力”面板接受任意非空 seed，可运行 1、10、100 或 500 局，支持暂停及两次同 seed 比较。模拟器将同一个 `RandomSource` 注入牌实例创建、洗牌和 AI 合法弃牌选择；生产路径不传依赖时仍使用 `Math.random` 与 `crypto.randomUUID`。测试实例 ID 使用 `<seed>-<顺序>-<区域>`，便于从失败产物定位物理牌。

自动策略只从正式合法弃牌集合选择，并调用正式摸牌、弃牌、荣和、跳过鸣牌与流局结算入口。每个动作后检查 136 张物理实例、有效区域唯一性、每种牌不超过四张、固定 14 张王牌、当前玩家/phase、动态点数守恒及合法推进。相同规则、seed 和策略会得到相同牌墙、动作、最终状态与牌谱事件；不同 seed 至少产生不同牌墙。

失败时面板显示 seed、规则、动作索引和失败不变量，可导出完整 JSON，或将失败状态转换为 `TestScenarioV1` 后在正式牌桌继续操作。`npm run test:stress` 固定运行 500 局；`npm run test:stress:long` 固定运行 5000 局。两者均不属于普通 `npm test`，长测试用于手动或 CI 定时任务。

### STAB-011 界面与键盘实验室

“界面与键盘实验室”提供 `ResultDialog`、`ContinueMatchDialog`、`ExitGameDialog`、`MatchResultDialog` 四个真实组件入口。面板实时显示当前焦点元素、焦点是否仍在弹窗内、Escape 预期、背景点击预期及关闭后应返回的触发元素。

关闭策略保持既有业务语义：局结果、继续存档和比赛总结必须由明确按钮推进，Escape 与背景点击均不能关闭；未结束且未在保存中的退出确认可通过既有“继续游戏”取消，因此 Escape 和背景点击映射到同一取消回调。比赛已结束或正在保存的退出弹窗不可取消。

打开弹窗后，焦点进入标记的安全首选按钮；Tab 与 Shift+Tab 在可用控件间循环。弹窗存在期间，背景兄弟节点设为 `inert`，body 滚动锁定；关闭后恢复原滚动状态并将焦点送回仍存在的触发控件。项目未引入 Playwright，组件级键盘回归覆盖焦点循环和关闭策略；正式桌面分辨率矩阵由 STAB-012 浏览器验收覆盖，屏幕阅读器与真实浏览器焦点恢复继续按下方清单人工验收。

### STAB-012 桌面分辨率用例

正式牌桌当前只支持横屏桌面，固定逻辑画布为 1280×720，推荐视口为 1366×768 及以上。正常游戏、牌谱播放器和测试模式共同使用页面级 `DesktopTableViewport`；缩放值为 `min(availableWidth / 1280, availableHeight / 720, 1)`，牌桌组件本身不散落额外桌面断点。低于 1280 宽或 720 高时不继续压缩或渲染牌桌，而显示“当前窗口尺寸过小”、最低横屏要求和“返回菜单”。

用例中心登记 7 个 `UiInteraction` 用例：`STAB-012-1280X720`、`STAB-012-1366X768`、`STAB-012-1600X900`、`STAB-012-1920X1080`、`STAB-012-2560X1440`、`STAB-012-1279X720-TOO-SMALL`、`STAB-012-1280X719-TOO-SMALL`。前五项检查牌桌、四家区域、四方牌河、中央计分板、本家手牌和顶部操作区可见且页面无滚动；后两项检查明确拦截。用例只驱动视口与可见性检查，不修改规则状态。

1024×768、900×600、800×560、560×800、手机竖屏和手机横屏不属于本轮验收范围，不应通过缩小牌尺寸或改变牌河几何强行适配。响应式外壳保留布局配置入口；未来手机横屏可替换页面外壳或布局配置，不需要改写规则组件。

## 人工验收流程

1. 加载目标场景，确认顶部“测试环境”、场景 ID、控制玩家和初始不变量均正常。
2. 按场景步骤只使用正式牌桌按钮操作；全员默认手动，不会自动触发 AI。
3. 每次杠后核对固定槽位表：0～3 为岭上，4/6/8/10/12 为表宝，5/7/9/11/13 为里宝；槽位职责来自共享 `wall.ts` 模型。
4. 核对活牌墙、已用岭上、公开宝牌、结算前/当前供托、玩家点数合计、动态初始总点数、最近动作和合法动作摘要。
5. 导出测试牌谱，在播放器回放相同步骤并比较公开状态；需要时从该步骤再次转成场景。
6. 使用“重置场景”确认完全恢复初态，再导出/导入确认状态等价。
7. 在界面与键盘实验室依次打开四类弹窗，以 Tab/Shift+Tab 循环一周，检查 Escape、背景点击、页面滚动和关闭后的触发按钮焦点。
8. 运行七个 STAB-012 用例：五档支持尺寸核对无裁切、遮挡或页面滚动；两个不足尺寸核对提示和返回菜单，不把范围外手机尺寸记为失败。

## 调试、不变量与失败报告

调试面板逐动作检查牌实例总量、有效区域唯一性、每种牌上限、活牌/王牌记账、岭上唯一性、宝牌槽、玩家与 phase、点数加供托守恒，以及是否存在合法推进或已终局。失败时状态会保留，顶部显示红色警告；使用“复制失败报告”和“导出场景”附上场景 JSON、动作序号、最近动作、失败不变量及浏览器控制台异常。

“执行下一 AI 动作”只推进一次并调用正式 AI/引擎入口；测试模式不会自动循环。测试模式不得直接编辑分数、牌墙或副露，所有动作仍受正式合法性校验。

## 数据隔离

测试对局不调用普通继续游戏保存流程，也不会进入普通牌谱库。测试牌谱仅在工具栏显式导出，记录来源为 `test-mode`；普通比赛牌谱来源仍为 `local-match`。结束测试或返回场景库会丢弃未导出的测试状态。

存档用例只能获得测试中心创建或明确注入的 `TestStorageAdapter`，默认实现是内存 Map，不读取或写入浏览器的普通 localStorage。存储失败通过替换该适配器模拟，不修改正常保存实现。牌谱、固定种子和 UI 自动运行器也通过测试上下文显式注入；缺少运行器时状态为“需人工确认”。因此用例中心不会改变普通页面默认行为，也不会为测试建立绕过正式规则的对局动作函数。
