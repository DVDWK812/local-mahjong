# 开发者测试模式

测试模式用于把确定性场景加载到正式牌桌与正式规则引擎中，复现规则、计分、牌山、存档和回放问题。它不会自动写入普通继续游戏存档；生成的牌谱标记为 `source=test-mode`，需从工具栏显式导出。

## 启用方式

- Vite 开发环境（`import.meta.env.DEV`）自动显示首页“测试模式”入口。
- 非开发环境仅在构建时设置 `VITE_ENABLE_TEST_MODE=true` 时启用。
- 已启用时可用 `?testMode=1` 直接进入场景库；未启用的普通生产构建不会显示入口，也不会响应该参数。
- 测试场景库、牌桌工具栏和调试面板均显示“测试环境”标识。

## TestScenarioV1 格式

`version` 当前固定为 `1`。场景复用可序列化的 `FullRuleConfig` 和 `GameState`，并补充 `id`、名称、说明、关联审计编号、局序、全员手动列表、声明牌数、动态初始总点数、已使用岭上牌数、杠前活牌数、人工步骤和可选检查点。

`gameState` 保存四家完整手牌、牌河、副露、分数与临时状态，以及场风、局数、本场、供托、当前玩家、phase、当前摸牌、所有等待窗口、准确活牌顺序和固定 14 张王牌。内置场景的 `instanceId` 使用可读且稳定的 `<scenario-id>-<zone>-<index>` 形式，不依赖随机 UUID。

启动前会严格校验版本、字段路径、四名唯一玩家、实例 ID、每种牌/赤牌上限、声明牌数、手牌与 phase、牌墙和王牌、当前摸牌、共享宝牌槽、岭上记账、动态点数守恒及 pending 窗口。claimed 牌河历史继续沿用项目的受控历史别名语义；校验失败会列出路径和原因并阻止启动。

## 测试用例目录与结果

首页目录用 `TestCaseDefinition` 包装现有 `TestScenarioV1`，只增加 `version`、`type`、关键词、操作步骤、预期结果和人工检查项，不改变场景或正式状态结构。类型固定为 `automatic`、`visual`、`hybrid`；视觉和混合用例必须提供写死的三组人工说明。

首页显示通过、失败、待测试、阻塞统计，并可按类型、状态和关键词筛选。每张卡显示当前状态、用例版本、最后测试时间和“开始测试”。运行中可判定通过、失败或阻塞。结果保存为 `{ caseId, caseVersion, outcome, testedAt }`；当目录中的用例版本变化，版本不匹配的旧结果显示“需复验”，并计入待测试。

## JSON 导入与导出

JSON 导入区默认折叠。可粘贴 JSON 或选择 `.json` 文件，并使用字段校验、格式化、复制和“校验并加载”；字段校验复用正式 `TestScenarioV1` 校验器。内置“地和”示例由 `getChiihouExampleScenario()` 通过真实场景构造器生成，测试会验证其字段、JSON 往返和正式 `canTsumo` 的地和判定，不手写猜测字段。牌桌工具栏可导出当前状态为新的 `TestScenarioV1`、重置到最初状态、复制状态摘要，或导出本次正式事件记录器生成的测试牌谱。

## 从牌谱创建场景

测试模式启用时，牌谱播放器显示“转为测试场景”。转换使用当前播放步骤的 `buildReplayState` 结果，并带入保存规则、四家状态、牌河、副露、牌墙、固定王牌、分数、供托、当前玩家和 phase。缺少完整活牌墙/14 张王牌的旧牌谱会禁用转换并显示原因；成功后场景脱离播放器，由正式引擎继续操作。

## 内置 STAB-001 场景

- `STAB-001-ANKAN`：当前玩家可立即暗杠。
- `STAB-001-MINKAN`：位于可直接选择明杠的鸣牌窗口。
- `STAB-001-KAKAN`：已有碰副露且持有第四张牌，可立即加杠。
- `STAB-001-FOUR-KANS`：按说明连续执行四次暗杠，不依赖随机摸牌。

每个场景包含人工步骤和检查点，记录期望岭上牌 `instanceId`、新公开表宝原始槽位、活牌剩余变化及回放状态。

## 立直弃牌与等待预览场景

- `RIICHI-DISCARD-MUST-TENPAI`：自动逐个执行两个产生不同等待的立直弃牌候选，检查具体 `instanceId`、宣言牌、立直状态、正式听牌与预览等待完全一致；不听牌弃牌必须被正式入口拒绝。
- `UI-RIICHI-DISCARD-WAIT-PREVIEW`：在正式立直操作框中用鼠标悬停/移出和键盘聚焦/失焦切换两个候选，检查等待牌种、每种剩余枚数、总有效枚数及清除行为；提示框与操作框并排显示。

赤五与普通五的自动回归按具体 `instanceId` 分别执行，确认弃牌后保留的是另一张物理牌，不按共享的 `tile.id` 误删。

## 番缚听牌场景

- `RULE-MINIMUM-HAN-2`、`RULE-MINIMUM-HAN-3`、`RULE-MINIMUM-HAN-4`、`RULE-MINIMUM-HAN-5` 分别启用二番缚、三番缚、四番缚和满贯缚。
- 每个场景的玩家 1、2、3 分别持有低于、等于和高于门槛一番的真实 13 张听牌手牌；场景名称直接标出牌型及正式役种番数。
- 低于门槛仍显示听牌、等待牌和剩余枚数，但等待牌标记“番数不足”；等于或高于门槛显示为可和。
- 二番缚示例依次为仅断幺九、断幺九＋一杯口、门清混一色；仅断幺九叠加河底捞鱼等正式役后达到二番门槛。
- 自动回归测试使用正式 `evaluateWin` 与共享番缚判定核对 1～6 番，不把宝牌、里宝牌或赤宝牌计入门槛。

## 人工验收流程

1. 加载目标场景，确认顶部“测试环境”、场景 ID、控制玩家和初始不变量均正常。
2. 按场景步骤只使用正式牌桌按钮操作；全员默认手动，不会自动触发 AI。
3. 每次杠后核对固定槽位表：0～3 为岭上，4/6/8/10/12 为表宝，5/7/9/11/13 为里宝；槽位职责来自共享 `wall.ts` 模型。
4. 核对活牌墙、已用岭上、公开宝牌、四家分数/供托、最近动作和合法动作摘要。
5. 导出测试牌谱，在播放器回放相同步骤并比较公开状态；需要时从该步骤再次转成场景。
6. 使用“重置场景”确认完全恢复初态，再导出/导入确认状态等价。

## 调试、不变量与失败报告

调试面板默认完全关闭，避免右下角摘要遮挡鸣牌操作；需要时从顶部工具栏展开，并按“摘要、不变量、合法动作、日志、牌墙、实例、原始状态”七组呈现。测试模式中的牌局分析抽屉会避开顶部测试工具栏，保证“关闭牌局分析”按钮始终可操作。调试面板逐动作检查牌实例总量、有效区域唯一性、每种牌上限、活牌/王牌记账、岭上唯一性、宝牌槽、玩家与 phase、点数加供托守恒，以及是否存在合法推进或已终局。失败时状态会保留，顶部显示红色警告；使用“复制失败报告”和“导出场景”附上场景 JSON、动作序号、最近动作、失败不变量及浏览器控制台异常。

“执行下一 AI 动作”只推进一次并调用正式 AI/引擎入口；测试模式不会自动循环。测试模式不得直接编辑分数、牌墙或副露，所有动作仍受正式合法性校验。

顶部“完全控制”开关启用后，人类接管所有座位，控制玩家会在每个正式动作完成后自动跟随新的 `GameState.currentPlayer`；关闭后可继续手动选择固定控制玩家。牌局工具栏不提供重复的“结束测试”按钮，使用“返回用例库”离开当前场景。

测试模式的桌面座位映射固定以玩家 1 为南家。切换观察/控制玩家只替换本家可见手牌和动作目标；牌河、头像、座位、风位、点数、庄家标记与副露方向继续使用正式牌桌的固定映射，不随“完全控制”轮转。

## 数据隔离

测试对局不调用普通继续游戏保存流程，也不会进入普通牌谱库。测试结果只写入独立版本化键 `local-mahjong.test-mode.case-results.v1`，其 envelope 也带 `version: 1`；它不复用普通存档或牌谱 Storage adapter。测试牌谱仅在工具栏显式导出，记录来源为 `test-mode`；普通比赛牌谱来源仍为 `local-match`。结束测试或返回场景库会丢弃未导出的测试状态，测试用例结果仍保留在独立键中。
